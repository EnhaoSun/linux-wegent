# Windows 微信本地数据库机制：源码研究笔记（第一轮）

> 研究日期：2026-10-31。研究对象：[wechatauto-replica](https://github.com/fanyuantaier/wechatauto-replica)。本文件是静态源码审计，不代表已完成实机验证。

## 一、研究结论

该项目的聊天记录读取主要依靠本地数据库，而非向微信服务器请求历史消息。Windows 微信进程负责正常登录和同步；外部程序定位账号数据目录、获取能够解密数据库的密钥材料，验证后解析消息。

**必须区分两类功能：**
- 数据库读取：本地查询、解密、消息解析；
- 客户端自动化：UIA、OCR、发送、窗口控制。后者不在 Linux 只读 MVP 的范围内。

## 二、关键模块

| 环节 | Windows 项目中观察到的机制 | Linux 研究重点 |
|---|---|---|
| 进程定位 | 查找正在运行的微信进程 | 进程发现与账号绑定 |
| 内存访问 | 使用 Windows 系统提供的跨进程读取接口 | Linux 访问权限与可行性 |
| 密钥获取 | 存在候选密钥扫描与旧版配置恢复两条路径 | 研究版本差异，不照搬偏移 |
| 密钥验证 | 利用目标数据库第一页进行密码学校验 | 复用校验算法及合成测试 |
| 数据解密 | 将数据库转换为可查询的本地缓存 | 优先采用 Linux 已有实现 |
| 多分片查询 | 处理分片 ID、发送者映射 | 验证 Linux 消息 Schema |
| 消息监听 | README 提供监听功能 | 第二轮确认具体轮询、游标和去重实现 |

主要源码：[wechatauto/db.py](https://github.com/fanyuantaier/wechatauto-replica/blob/main/wechatauto/db.py)。

## 三、最重要的版本差异

当前 `db.py` 明确将 Config.Cipher 相关扫描列为优先路线；旧版配置恢复主密钥的方法在较新的 4.1.13+ 版本可能无法复现有效数据库密钥，因此作为回退。

这说明不能把 Windows 的成功简单归结为“读取内存就能拿到主密钥”。内存中具体有什么结构、是否能找到有效材料，与客户端版本密切相关。

## 四、为什么必须验证密钥？

内存里有大量随机性很强的字节，不能仅凭长度或外观认定为密钥。项目通过目标数据库的密码学完整性校验判断候选材料是否正确。此逻辑相对独立于操作系统，值得复用。

同时要区分“主密钥”和“逐数据库密钥”：不同数据库可能有不同的盐及密钥派生结果。

## 五、多分片与多账号问题

README 的修复记录表明：
- 不同消息分片的本地 ID 可能重复；
- 发送者数字 ID 需要使用消息所属分片的映射表；
- 不能把某个固定数字直接认定为本人；
- 多账号运行时不能只凭数据库目录修改时间决定当前账号。

Linux Connector 必须在事件 ID 中保留账号与分片维度，避免错读和重复。

## 六、Windows 与 Linux 的分界

**可以复用：** 密钥校验思路、数据库格式测试、消息规范化规则、增量游标与去重设计。

**需要重做：** 进程权限、内存对象定位、Windows 特有的二进制布局和账号目录发现。

**优先采用 Linux 现成实现：** [chatlog-keeper](https://github.com/labazhou2024/chatlog-keeper) 的数据库快照、WAL 处理与解析基础。

该 Linux 项目记录的 4.1.13.9 成功取钥案例采用启动期调试器观察；这不等于被动只读扫描已成功。

## 七、第二轮源码审计任务

1. 固定上游提交版本，并建立函数与行号索引。
2. 追踪 Windows 数据库缓存刷新、SQL 查询与消息分片合并。
3. 定位监听模块的调用链，确认轮询周期、去重和重启补查机制。
4. 对比 Linux 端的数据格式、权限边界与快照能力。
5. 用合成数据库测试解析和事件一致性；授权实机验证另行记录。

## 八、风险边界

只读访问不等于完全不可检测。项目公开的成功案例不能证明所有版本、所有账号都安全。研究过程中不收集第三方账号密钥，不记录原始聊天内容，不修改官方微信客户端，也不将敏感数据库上传云端。
