# MVP 产品与技术方案（v1）

更新：2026-11-01

## 1. 目标与用户
目标用户：使用个人微信开展工作、需要同时跟进多个客户/项目/工作群的人。
核心痛点：
- A：信息多，重要消息被淹没，容易漏回复或忘记承诺。
- C：跨天、跨会话的任务状态难以掌握，不知道哪些事项被阻塞或尚未完成。

核心价值：把用户选择的工作聊天转成可追溯的工作事项和进度变化。

## 2. MVP 用户流程
1. 启动 Linux 微信并登录（用户亲自扫码）。
2. 在本地管理界面查看可识别的会话候选列表；如果 AT-SPI 无法列出，先手动登记并定位。
3. 用户勾选 1–5 个工作会话；默认全部不选。
4. 用户点击“采集一次”；Collector 仅进入所选会话，读取 UI 中可见的消息和必要的少量上下文。
5. UI 结构化消息 → 本地存储 → 去重 → 事件/事项抽取 → 人工确认重要状态。
6. 工作 Inbox 展示：需处理、等待他人、阻塞、已完成、待核实；每天生成简报。
7. 用户随时暂停、取消关注或删除对应会话及其数据。

## 3. 关键边界
- 首版不要求读取历史 7–30 天：可读取的历史深度以 UI 验证结果为准。
- 不自动发送消息、不主动群发、不操作数据库、不 Hook、不注入、不解密。
- 只读取用户授权的会话；任何新会话必须再次授权。
- 不以会话名称作为永久 ID；需要验证头像/名称/成员等 UI 特征，身份不确定则停止并要求确认。
- 采集可能漏消息、漏时间戳、漏发送者；必须标记不完整，不得推断“对方未回复”。
- 聊天涉及第三方个人信息：优先本地处理、最小化保留、提供删除与脱敏；外部模型调用前须单独授权并评估合规与平台规则。
- AT-SPI 不保证规避微信检测或封号风险；如果需要高频 UI 自动操作，应重新评估。

## 4. 组件划分
- Collector：Python + PyGObject/AT-SPI（具体接口以实验结果为准）；只负责可见 UI 读取。
- Normalizer：统一消息格式、发送者、时间戳、来源、置信度、采集批次。
- Storage：SQLite；会话白名单、消息、证据、检查点、健康记录、事项及状态历史。
- Work Engine：事件提取、事项关联、状态更新、去重、证据引用、待确认队列。先规则+可替换 LLM 接口。
- UI：先用最小本地 Web 页面或 CLI 验证；不追求漂亮界面。
- Briefing：本地按需生成每日摘要；自动定时任务放到后续阶段。

## 5. 采集数据契约（草案）
Conversation: local_id, display_name, identity_fingerprint, user_selected, last_verified_at
Message: local_id, conversation_id, sender_label, text, displayed_time, observed_at, capture_batch, source_locator, content_hash, confidence
CaptureBatch: id, conversation_id, started_at, ended_at, status, completeness, error
WorkItem: id, title, owner, due_at, state, confidence, last_evidence_message_id
WorkItemEvent: id, work_item_id, message_id, event_type, observed_at

说明：content_hash 不能单独作为去重键（同一句话可能重复出现）；时间戳可能只有相对时间。无法证明连续性时标记 gap/unknown，不声称“增量完整”。

## 6. 分阶段验收
### P0：环境与控件树可行性
- Ubuntu Desktop 图形会话、Linux 微信可运行、AT-SPI 可连接。
- 读取并保存脱敏控件树快照。
- 判定能否区分会话列表/当前聊天/消息正文/发送者/时间。
- 如果消息正文无法通过 AT-SPI 获得，记录 No-Go，**不自动转向 OCR、内存读取或解密**。

### P1：指定会话单次采集
- 只采集用户指定的 1 个会话。
- 展示采集条数、原文、来源、失败项、完整性状态。
- 重复采集不产生重复记录；同文不同消息不误删。
- UI 操作受限速、可中断，遇到身份不确定停止。

### P2：多会话与增量
- 选择 3–5 个会话；未选会话不进入、不保存内容。
- 支持手动重复检查；重启恢复检查点。
- 检测无法确认的时间断层并显式标记，绝不静默声称同步成功。
- 稳定后才考虑低频自动检查。

### P3：工作事项
- 识别任务、承诺、负责人、截止时间、风险、完成/延期事件。
- 同一事项跨多条消息关联；冲突信息进入待确认。
- 每条事项可回溯原始消息；采集不完整时不做确定性未回复判断。
- 基于人工标注样本评估精确率、漏报率和状态更新正确率。

### P4：本地 Inbox 与 Briefing
- 展示需处理、等待他人、阻塞、完成、待核实。
- 每日简报区分新事项、状态变化、待确认。
- 支持用户纠错，纠错写入事件历史。

## 7. Go / No-Go
- P0 若无法读到消息正文、身份识别不可靠或 UI 操作对账号有明显风险：停止 UI Collector 路线，保留工作事项引擎，用用户主动导入的合成/脱敏聊天验证价值。
- P1/P2 若无法保证消息完整性：可做“发现可能的重要事项”，但不得承诺实时监控或无遗漏。
- 产品价值验证：至少 5 组真实但已脱敏的工作对话，人工标注任务及状态；统计有效提醒、错误提醒、漏报与用户实际节省的时间。

## 8. 本阶段不做的研究
Windows 只读内存复刻、chatlog-keeper 数据库解密、MimicWX 数据库路径、云 Windows 多租户、全量同步。旧方向不作为当前执行依赖。
